**Standkreis Atlas — architecture, code, DX, design and UX review**

Reviewed 8 September 2026, commit `bd5fbfa`. This is a repository and local runtime review, not an audit of the deployed Vercel environment. I did not change application source.

Concurrent branding edits appeared near the end of the review: icons, metadata, an onboarding brand component and headline/button copy. I inspected that diff and left it untouched. The screenshots, measurements and behavioral results describe the earlier audited build; they do not certify the new branding work. Source line references describe the baseline and may shift as those edits land.

**Overall assessment.** This is a coherent, working early product with a distinctive visual identity and unusually substantial field-testing history. Keep the stack and the sightings-based domain model. The main weakness is consistency across boundaries: identity adoption, browser persistence, object deletion, background jobs, content provenance, and the promises made in the interface. These need attention before expanding the audience or generating another region's prose.

The normal journey works: choose a region, browse, open a species, save a wild sighting, see the collection fill, and reopen the atlas without a network. The failures found below mostly require a less convenient situation: concurrent requests, recovering an existing identity, a missing database, deleting a cached photo, or an interrupted local write.

**What I checked.** I reviewed routing and layouts, the Prisma schema and migrations, all router areas, identity/passkey/email flows, uploads and storage, query persistence, the outbox and service worker, the main components and translations, ETL/content/prose boundaries, build/deployment configuration, tests, and the current roadmap and handoffs. I exercised the production build in headless Chrome at 390 × 844 and 1440 × 900, with German/English and light/dark screens. Local test identities and their database records were removed afterward. Paid identification and real email delivery were disabled; no deployment, migration, production write, or paid model call was performed. Native passkey ceremonies, physical iOS behavior, screen-reader operation, production load, and scientific accuracy across the full dataset remain outside this verification.

**Architecture: retain the modular monolith, strengthen its boundaries.**

| Area | Assessment |
| --- | --- |
| Domain | `Sighting` as the atom, derived discovery/progress, separate study state, and regional plausibility are good foundations. Wild/captive distinction is consistently meaningful. |
| Application | Next.js is mostly delivering a client application and typed backend here. That is a defensible choice for an offline-capable phone product. Moving everything into server components would not solve its main problems. |
| API and database | tRPC, Zod and Prisma give useful end-to-end contracts. Owner-scoped reads/writes and relational cascades are good. Multi-step operations still need stronger atomicity and behavioral integration tests. |
| Client state | React Query, URL state and persisted snapshots make normal navigation fast. The outbox adds substantial value. Several independent stores lack a shared identity/version/deletion lifecycle. |
| Content | Source attribution, facts, interaction provenance, validation and cached prose are thoughtful. Regional prose is currently stored at global taxon scope, and an adverse audit verdict does not prevent publication. |
| Operations | Keeping intensive ETL on the laptop is reasonable at this stage. Importing its disk-cache implementation into runtime routes creates build and job-lifecycle coupling. |

I would introduce small internal seams for identity/session lifecycle, outbox persistence, content readers versus ETL writers, and domain mutations with shared cache invalidation. This does not require microservices or a repository-wide rewrite. Preserve the pure functions already extracted for plausibility, grouping, search, and content parsing.

**Prioritized findings.** P1 means address before broader public use or before the affected rollout. P2 means a concrete reliability, accessibility, or maintainability issue worth scheduling next. “Confirmed” means reproduced in this review; “source” means the path is evident in code but its failure scenario was not exercised.

**F01 · P1 · The privacy promise contradicts the implemented data flow. Confirmed in rendered copy and source.**

Onboarding says exact places never leave the phone, and settings describes an anonymous identity as “Only on this phone.” In reality, anonymous sightings are uploaded to Postgres; exact latitude/longitude are sent by the save flow, stored by `sighting.create`, and forwarded to GBIF for reverse geocoding. Uploads also go to server storage before any recovery method is attached. The sighting map requests location-specific zoom-16 tiles directly from OpenStreetMap.

Decide the intended policy, then make storage, external requests, onboarding and settings agree. If retaining the current implementation, explain that records are private to the user but stored on the server, and that passkeys/email enable recovery rather than initiate synchronization. This finding concerns factual product behavior, not a legal-compliance conclusion.

**F02 · P1 · Public expensive operations have no application-level budget. Source.**

`sighting.identify` checks ownership but does not limit calls per identity, photo, address, or overall budget. Uploading creates an anonymous identity when necessary and has no storage quota. `dex.requestRegion` remains callable by an anonymous client and can start a region/content job even though region creation is deliberately unavailable in the UI. The search and tile buckets do not protect these operations; an upstream 429 is not an app budget.

Add durable scan and storage quotas, concurrency limits and a spending cutoff; coalesce/reuse identification for the same photo and model version. Enforce region-creation availability on the server. Preserve anonymous use, but make expensive capabilities explicitly bounded. No abusive requests or paid calls were sent during this review.

Evidence: [sighting.ts:115](../../app/src/server/routers/sighting.ts#L115), [photo/route.ts](../../app/src/app/api/photo/route.ts), [dex.ts:196](../../app/src/server/routers/dex.ts#L196), [identify.ts](../../app/src/server/identify.ts).

**F03 · P1 · Recovering an identity fails when the source identity has an avatar. Confirmed.**

The merge assigns the source's `avatarAssetId` to the target before releasing the source's unique reference. A valid email verification into an identity without an avatar returned HTTP 500: `Identity_avatarAssetId_key`. The email code had already been consumed outside the merge transaction, making the failed recovery harder to retry. The shared merge is also used by passkey adoption.

Clear the source reference before transferring it inside the same transaction. Make successful code consumption and identity adoption atomic. Specify what happens to existing recovery methods, duplicate sightings and their photos; the current merge deletes duplicate sighting assets through cascades without deleting their stored files.

Evidence: [identity.ts:32](../../app/src/server/routers/identity.ts#L32), [identity.ts:65](../../app/src/server/routers/identity.ts#L65), [identity.ts:281](../../app/src/server/routers/identity.ts#L281), [schema.prisma](../../app/prisma/schema.prisma).

**F04 · P1 · Deletion does not remove all copies of a private photo. Confirmed cache behavior; storage-failure path from source.**

A test photo returned 200, was deleted successfully, then still returned 200 at the original URL through the service worker. A cache-bypassing URL returned 404. Private images share the identity-independent `dex-images` cache; neither individual deletion nor identity deletion purges it. `watchIdentity` clears query persistence, not photo caches or scan metadata. Server cookie checks cannot protect a response served entirely from this cache.

Separately, the storage removal helper catches every Blob/disk deletion error and reports success. Subsequent deletion of the database row loses the reference needed to retry a failed removal.

Give private cache entries an identity lifecycle and purge them on deletion/adoption as appropriate, including other open tabs. Distinguish already-missing objects from storage failures and retain retryable deletion work until confirmed. Keep shared reference images separate from private photos.

Evidence: [sw.js:190](../../app/public/sw.js#L190), [IdentityDelete.tsx:33](../../app/src/components/IdentityDelete.tsx#L33), [client.tsx:106](../../app/src/trpc/client.tsx#L106), [photos.ts:79](../../app/src/server/photos.ts#L79).

**F05 · P1 · The outbox can acknowledge a photo without durable storage. Source.**

When IndexedDB hangs, `write()` resolves after the timeout and keeps a memory copy. Its localStorage fallback explicitly excludes blob rows. An offline photo can therefore appear saved even though closing the page loses its only usable copy; a scan can later reach `photo gone`. The current timeout tests cover study rows, not photo durability.

There are related lifecycle gaps: photo upload completion removes the local blob before persisting the parent row's server photo ID, and queued rows carry no owner identity. `QueueFlusher` starts independently of identity verification; clearing a store does not cancel an already-running flush.

Define “saved” as durably persisted. Show a recoverable storage failure when a photo cannot be retained. Persist upload acknowledgment before removing the blob, use atomic transactions for related records, and give queued work an explicit owner plus cancellation/generation boundary.

Evidence: [Queue.ts:60](../../app/src/components/Queue.ts#L60), [Queue.ts:97](../../app/src/components/Queue.ts#L97), [Queue.ts:138](../../app/src/components/Queue.ts#L138), [Queue.ts:205](../../app/src/components/Queue.ts#L205), [QueueFlusher.tsx:18](../../app/src/components/QueueFlusher.tsx#L18).

**F06 · P1 · The checked-in CI cannot reproduce the locally green check. Confirmed dependency.**

The workflow provisions no database and states that export needs none. Species `generateStaticParams` queries the database. With the existing local DB, export succeeds; with `DATABASE_URL` pointed at an unreachable local port, it fails with `P1001` while collecting species page data. The workflow has no service, migration, fixture or environment setup to satisfy that dependency.

Use a disposable database with deterministic fixtures in integration/build CI, or make the export route list a versioned build input. Also run the production server build: export omits API routes and cannot validate the code shipped as functions. This is a reproducible workflow defect, not a claim about an inspected GitHub Actions run.

Evidence: [check.yml](../../.github/workflows/check.yml), [species page:8](../../app/src/app/[locale]/species/[gbifKey]/page.tsx#L8), [package.json](../../app/package.json).

**F07 · P2 · Sighting creation is only sequentially idempotent. Confirmed.**

Eight simultaneous creates with the same client-generated ID produced one 200 and seven 500s from `Sighting_pkey`. The initial lookup and subsequent insert race. Two tabs can each flush because the client lock is only module-local. Later retries can recover, but the endpoint does not deliver the promised idempotent response under concurrency.

Catch the unique conflict and return the existing owned sighting, or use an atomic database operation followed by ownership validation. Test simultaneous retries and photo binding together.

Evidence: [sighting.ts:75](../../app/src/server/routers/sighting.ts#L75), [sighting.ts:88](../../app/src/server/routers/sighting.ts#L88), [Queue.ts:256](../../app/src/components/Queue.ts#L256).

**F08 · P2 · Email attempt limits are not atomic. Confirmed.**

Twelve simultaneous wrong-code requests incremented a test code to nine attempts despite the intended maximum of five. Reading the count, checking it and incrementing happen separately. Code consumption has the same read-then-update shape; send limits also count before creating a new row.

Use conditional database updates or transactional locking to claim an attempt and consume a live code once. Test concurrent verification and sending, not only sequential cases. This review did not demonstrate account takeover.

Evidence: [identity.ts:252](../../app/src/server/routers/identity.ts#L252), [identity.ts:272](../../app/src/server/routers/identity.ts#L272).

**F09 · P2 · Region-specific prose is stored as one global taxon value. Source; current prose rendered.**

The prompt and ecology sheet use the reader's region and its seasonal profile. The writer stores one `Taxon.prose`, and the reader returns it regardless of `regionId`. A shared species processed for another region overwrites the previous text. The fire salamander currently explicitly describes Mainz-Bingen; that same text is available when reading it from another region.

Before another region run, either keep global prose region-neutral and render seasonal context separately, or key regional text by taxon, region and content version. The facts' hash is not a substitute for matching the reader's region.

Evidence: [sheet.ts:74](../../app/etl/prose/sheet.ts#L74), [prompts.ts:25](../../app/etl/prose/prompts.ts#L25), [step.ts:83](../../app/etl/prose/step.ts#L83), [taxon.ts](../../app/src/server/routers/taxon.ts).

**F10 · P2 · The prose audit labels unsupported content but does not block it. Source.**

`validateAudit` checks verdict shape and sentence count. `proseFor` then assembles and stores the draft even if the auditor labels its sentences unsupported. Missing direction templates are counted, also without stopping publication. The UI renders the text and an aggregate judge count across languages/variants.

Define an explicit publication gate for unsupported and partial sentences, retry or quarantine failures, and present validation in terms a reader can use. Five taxa have prose among 1,869 distinct taxa in regional sets in the local DB; the coverage limitation is already acknowledged in the roadmap. A passing model audit should not be presented as scientific verification.

Evidence: [validate.ts:35](../../app/etl/prose/validate.ts#L35), [step.ts:97](../../app/etl/prose/step.ts#L97), [Prose.tsx:27](../../app/src/components/Prose.tsx#L27).

**F11 · P2 · Modal semantics and keyboard behavior disagree. Confirmed.**

After focusing and opening the filter button, pressing Tab moved to a species link behind the modal. `Sheet` declares `aria-modal` but provides no initial focus, focus containment, background inertness, or focus restoration. Its shared implementation spreads the issue to region, source, sign-in, and deletion sheets. Escape handling is present and useful.

Implement the full dialog lifecycle centrally, including nested sheets and scroll locking. Audit custom radios/tabs for their expected keyboard interaction and give inputs persistent accessible labels. The [W3C modal-dialog pattern](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/) describes contained tab navigation and focus placement/return.

Evidence: [Sheet.tsx:51](../../app/src/components/Sheet.tsx#L51), [FilterDrawer.tsx:71](../../app/src/components/FilterDrawer.tsx#L71), [IdentityEmail.tsx](../../app/src/components/IdentityEmail.tsx).

**F12 · P2 · Several meaningful text/color combinations fail contrast requirements. Measured.**

White on light moss is 3.30:1; white on dark-theme moss is 2.28:1. White on amber is 4.12:1 in light and 2.15:1 in dark. The species action labels use 17px bold text, which requires 4.5:1. Light-theme faint text on paper is 2.32:1, yet this token carries state, missing-data and provenance information. The issue is particularly relevant to an outdoor app.

Use separate tokens for filled control backgrounds and text/icon colors; the current “deep” token changes to a bright foreground in dark mode, so blindly replacing all button fills with it will not fix both themes. Preserve the brand palette while checking actual foreground/background pairs. [W3C contrast guidance](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html) requires 4.5:1 for normal text and 3:1 for large text.

Evidence: [tokens.css](../../app/src/styles/tokens.css), [SpeciesPage.tsx:308](../../app/src/components/SpeciesPage.tsx#L308), [Prose.tsx:34](../../app/src/components/Prose.tsx#L34).

**F13 · P2 · Runtime imports pull the ETL disk cache into local server traces. Confirmed.**

The production tRPC and cron route traces each list 37,742 files, including 37,029 ETL cache files. Referenced file sizes total about 1,835 MiB, of which 1,816 MiB is cache. No `.env` files appeared in those traces. This measures the local populated checkout, not a deployed Vercel bundle; the ignored cache should be absent from a clean checkout.

Separate runtime HTTP clients and pure domain helpers from the ETL's filesystem cache. Constrain file tracing and inspect the function artifact from a clean build. This is also a DX problem: results and build costs vary sharply with the developer's cache contents.

**Design and UX: preserve the visual identity, improve recognition and the first minute.**

The paper/moss palette, nature photography, rounded surfaces, large species hero, and green/amber distinction form a consistent product. The central logging action, explicit wild/kept save choice, source sheets, reduced-motion handling and forgiving empty content states are useful. The main UX limitation is that collection state and data machinery sometimes take precedence over identifying and learning about an organism.

**Developer experience and test strategy.** The historical records make decisions traceable and the pure tests run quickly. However, 530 tracked files are under `app/scripts` and 615 under `docs`, out of 1,326 total tracked files. Many are fixtures/images rather than active code, but a newcomer must distinguish current contracts from exploratory evidence and superseded handoffs. Comments frequently describe milestone history or intended guarantees more strongly than the implementation supports.

Keep the archive, but add one short current architecture/setup guide and a small named set of supported verification commands. Organize application modules by feature where it improves ownership; extract query/mutation orchestration from the larger components rather than merely splitting their JSX. Add runtime schemas at persisted-JSON boundaries and an explicit cache schema version. Avoid importing shared client types from a directory named `server` even when the current module is technically pure.

The important missing tests are behavioral integration tests: concurrent create, avatar adoption, single-use email verification, deletion across disk/Blob/browser cache, two-tab outbox flushing, identity change with pending work, interrupted photo acknowledgment, and storage failure. Several files named as router/component tests exercise helpers rather than the HTTP/database/DOM behavior implied by their names. Existing CDP scripts are useful foundations, but should make assertions fail the command; a recorded null field must not silently count as a successful check. Run a small production-build browser suite in CI for onboarding → save → journal → offline reload, plus keyboard dialog behavior. There is no need to add tests for every styling utility.

**Suggested order of work.**

1. Correct the privacy contract; bound scans/uploads/region creation; fix avatar adoption and complete deletion.
2. Make CI reproducible, include the server build, and add regression coverage for the reproduced failures.
3. Stabilize outbox durability, identity transitions, photo acknowledgment and concurrency; fix dialog focus and contrast alongside this work.
4. Fix regional prose scope and publication gates before expanding generation. Separate runtime content reads from ETL cache/job implementation.
5. Improve first-run action visibility, navigation labels, species-name readability and the species learning hierarchy; validate those changes on another real walk.

The next milestone should be a focused reliability and usability pass. The core product and stack are worth retaining; expanding features now would multiply several unresolved lifecycle and content problems.
